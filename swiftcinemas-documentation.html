SwiftCinemas: current architecture

How the iOS app, backend services, and configured infrastructure work together.

Architecture explanation + selected reference Source-reviewed Not a live-deployment audit

Revision: October 22, 2026. Written for product and architecture stakeholders; the reference sections support developers reviewing client/backend interactions.

The current system in five points

  • UIKit remains the app foundation. View models have been extracted for a scoped set of screens; SwiftUI is integrated in selected areas, not adopted as a uniform app lifecycle.
  • One app-owned networking stack is shared. AppDelegate.services creates the client, response cache, and service wrappers, then injects the container into shared data managers.
  • The public reverse proxy is not the application gateway. Catalog and seat requests route to mbooks; checkout and purchases use dalogin, which forwards selected authenticated calls.
  • Seat selection is local until checkout. The backend checks availability under database locks. Reservation commits precede external payment; payment failure invokes compensating cancellation.
  • Freshness and delivery have limits. GET response caching is opt-in. Incoming screen-news events are currently logged by iOS, not guaranteed to refresh a view or display an alert.

Scope: component ownership, representative flows, seat rendering and data lineage, headers/statuses, and simplified endpoint payloads. Installation steps, project history, exhaustive file inventories, future roadmaps, and step-by-step admin procedures are intentionally outside this page.

3. Representative interaction flows

Catalog to rendering, then seat selection

  1. MoviesVC asks its view model to load browse data. The view model calls MoviesDataManager.fetchPaging(query:), which calls MbooksService.moviesPaging.
  2. The wrapper constructs an Endpoint for GET /mbooks-1/rest/book/movies/paging. On a cache miss, APIClient sends it through URLSession, NGINX and Apache to mbooks' MovieController and MovieService—not through dalogin.
  3. The manager decodes movies into MovieDataModel values, updates browseList, and writes per-movie Realm cache entries. The view model updates state; its callback drives the controller's table reload.
  4. Movie selection is retained in MoviesDataManager.selectedMovie. The SwiftUI venues path receives explicit movie inputs, calls MbooksService.venue(movieId:) directly, and hands a selected venue into UIKit VenuesDetailsVC.
  5. VenuesDetailsViewModel.resolveContext() combines controller inputs with manager context and updates selected movie/venue values. It loads dates with GET /dates/{locationId}/{movieId} under the mbooks book root.
  6. ScreeningDateSelectionViewModel stores the chosen date ID/text. Venue details loads GET /seats/{screeningDateId} through SeatsDataManager, then presents PopOver. Local seat toggles build the basket; they do not reserve seats on the server.

Checkout: local intent to backend booking and payment

Retained because this flow explains where user intent becomes a reservation, which service owns payment, and why HTTP success alone cannot confirm a booking.

  1. BasketVC checks its in-progress guard and obtains a Braintree client token via BasketViewModel → CheckoutDataManager → LoginGatewayService → GET /login/CheckOut. Dalogin forwards to mbooks /rest/book/payment/clientToken.
  2. The SwiftUI CardFields sheet produces a payment-method nonce. Pay invokes the view model's submit(nonce:); Cancel clears the in-progress state.
  3. The view model generates a millisecond orderId and serializes the basket's screening-to-seat-number map. CheckoutDataManager sends form fields to POST /login/CheckOut. Dalogin adds session-derived authentication context and forwards to mbooks /rest/book/payment/fullcheckout2.
  4. CheckoutService reserves tickets via TicketService and DAO.bookTickets(). The DAO locks seats using PESSIMISTIC_WRITE before checking availability and commits reservation records before the external Braintree transaction.
  5. A failed payment result invokes compensating ticket cancellation. This is not an atomic database/payment transaction, nor a claim of atomicity across multiple screening entries or every exceptional failure.
  6. CheckoutResultModel interprets the returned JSON. BasketViewModel publishes the terminal result; on success it finalizes Basket → Seats → Dates context resets once. The controller presents the outcome and releases the in-progress guard.

Evidence: BasketVC.swift, ViewModels/BasketViewModel.swift, DataManagers/CheckoutDataManager.swift; dalogin servlets/CheckOut.java, client/filter/RequestFilter.java; mbooks rest/CheckoutController.java, service/CheckoutService.java, service/booking/TicketService.java, db/DAO.java.

A gateway example that targets mbook: screen-news settings

LoginGatewayService.putNewsScreen(enabled:) sends PUT /login/admin/newsSettings/screen. AdminServlet forwards the JSON and session-derived user to mbook /mbook-1/rest/news-settings/screen. The backend validates a boolean enabled; body ownership fields are ignored. Missing settings read as disabled. This proxy explicitly relays downstream status, media type, and body. A failed save must not be treated as a confirmed preference change.

Evidence: Networking/BackendServices.swift; dalogin servlets/AdminServlet.java, servlets/responsemap/AdminResponses.java, client/service/NewsSettings.java; mbook rest/NewsSettingsController.java, service/NewsSettingsService.java.

4. Seat-grid rendering reference

Retained to show exactly how backend seat properties become visible rows, prices, availability, and local selection. This is a UI/data contract reference, not a proposed seating redesign.

  → {"seatsforscreen": [SeatItem, …]}
  → SeatsDataManager.fetchSeats → [SeatModel] → allSeats
  → SeatSelectionViewModel.rowKeys / seats(forRowTag:)
  → PopOver UITableView
      → TableViewCell per row
          → horizontal UICollectionView tagged with the row index

Current layout and rendering mechanics
ConcernSource-backed behavior
Row identity/ordergetRows returns Array(Set(seats.map { $0.seatRow })).sorted(). Sorting is lexicographic string sorting, not numeric/natural row sorting. For example, "10" sorts before "2".
Seats within a rowseats(forRowTag:) resolves a row key and filters allSeats by seatRow. It preserves response order; it does not explicitly sort by seat number. Each row's item count is calculated independently.
LayoutPopOver uses one table section and 75-point table rows. TableViewCell creates a horizontal collection with 75 × 65-point items, five-point section insets, and multiple selection. storedOffsets preserves horizontal position per row index.
LabelsSeatCells.textLabel shows seatNumber. priceLabel shows Double(price) * tax followed by " Ft". This is the current display formula, not a guarantee that it equals the backend checkout total.
AvailabilityThe model maps the wire string isReserved == "1" to true. A reserved seat has a dark-gray background; an available seat is light gray. The view model will not add a reserved seat to the basket.
Selection stylingCells start with a one-point gray border. Selection/highlight handlers use four points; willDisplay reapplies four points for basket-selected IDs. Unhighlight and rejected/deselected paths can reset it to one point. The border is a local UI cue, not evidence of a backend reservation.
Toggle and cleartoggle requires selected date, movie, and venue context before adding a BasketItem. Re-tapping removes it. Clear removes the current screening payload and basket items for loaded seats, resets selection arrays, then reloads the table.

Layout and pricing boundaries

The current mbooks DAO.insertNewScreen() creates uniform rows from nrOfRows and nrOfSeatsInRow, uses an A–P label array for seat-number prefixes, and writes numeric row strings such as "1". The iOS renderer counts seats independently per row, but that does not establish an implemented variable-row admin contract or support for more than the generator's label range.

The grid's price * tax display differs from CheckoutService's accumulation of base price plus price * tax. This page records the difference; it does not invent a corrected tax rule, currency conversion, or rounding policy.

Checkout: form fields containing a JSON string

GET /login/CheckOut relays a response containing clientToken:

{"clientToken": "EXAMPLE_BRAINTREE_CLIENT_TOKEN"}

POST /login/CheckOut uses application/x-www-form-urlencoded. The following are decoded field values; the third value is a JSON string inside the form:

payment_method_nonce = EXAMPLE_NONCE
orderId = 1792706400000
seatsToBeReserved = {"seatsToBeReserved":[{"screeningDateId":"5","seat":"A1-B2-"}]}

orderId represents current milliseconds, not the returned purchase ID. seat contains dash-separated seat numbers with trailing dashes, not seat database IDs. The gateway resolves uuid for the downstream request.

Selected successful response fields, from CheckoutMapper and FullCheckoutResponse:

{
  "ResponseText": "hello",
  "purchaseId": 42,
  "Amount": 6.99,
  "TaxAmount": "3.99",
  "Success": "true"
}

The full response also includes processor fields (AuthCode, ResponseCode, Status), tickets, and seatsforscreen. This projection intentionally omits those nested/processor values. CheckoutResultModel recognizes ResponseText == "hello" or a decoded status equal to "success"; HTTP 200 or Success alone is not its success test.

A caught reservation conflict can return HTTP 200 with this business-failure shape:

{
  "Error": "Tickets are already sold!",
  "Success": "true",
  "Message": "Illustrative reservation failure detail"
}

The unusual "Success": "true" is current backend behavior, not a typo in this reference. An unsuccessful payment result instead returns an "Error with Transaction" field. Do not infer success from an isolated key or from the gateway's HTTP status.

9. Cross-client & operational dependencies

Retained only where operational behavior changes what a stakeholder should expect from the architecture: shared contracts, freshness, payment outcomes, and event delivery.

Caching is selective, not offline-first

APIClient reads/writes response cache only for GET endpoints with a cacheKey. RealmResponseCache uses a one-hour TTL. Paging and movie-to-venue requests opt in; direct date and seat calls do not. Movie/venue managers also maintain their own entries, and VenuesDataManager.getSeatsForScreen has an in-memory screen/date cache.

Consequently “no response-cache key on the seat GET” does not mean no seat data can ever be held locally. Local display is not an availability guarantee; checkout must recheck under backend locks.

Screen events are selective delivery

Successful screening create, update, and delete publish mbooks events through Kafka to mbook. Kafka's serialized Java event representation and WebSocket JSON are different contracts.

/mbook-1/ws requires a nonblank deviceId query parameter. Screen-news delivery resolves that device to exactly one distinct active user and checks their screen-news preference. This is not a send-to-all-connected-clients rule. iOS currently logs payloads and metadata; automatic alerts or seat refresh are not established behavior.

10. Evidence, assumptions & verification limits

Reading the source references: unqualified Swift paths are relative to SwiftCinemas/SwiftLoginScreen/. Java paths after a service name are relative to that module's src/main/java/com/dalogin/, com/jeet/, or (for images) com/example/. Infrastructure and .ai/ paths are repository-root relative.

  • Current-state basis: local source and configuration inspected for this revision. Older documentation and migration plans provide context, not authority over current implementation.
  • Existing artifacts consulted: .ai/specs/legacy-specify/features/SwiftUI_migration/speckit.migration.mvvm.implementation-plan.md records the scoped extraction and retained caches. The historical api-to-datamanager-mapping.md includes superseded names; this page uses the current Swift properties instead.
  • Illustrative data: examples describe shapes, not real catalogue records, valid credentials, approved prices, or operational test fixtures. Array order and omitted fields are not newly specified business rules.
  • One-argument dates helper: the Swift wrapper still exposes dates(screenId:), and a manager helper calls it. The inspected backend VenueController declares the two-argument /dates/{locationId}/{movieId} route, not a matching one-argument route. The former is documented as verified; end-to-end behavior of the one-argument helper remains unverified.
  • Image path composition: ImageResourceService.getData prepends URLManager.image, while some callers, including movie preloading, already apply that helper. Correctly resolved image fetching for those call sites is not asserted. The endpoint table describes the backend route, not proof that every current caller composes it correctly.
  • Pricing and selection limits: the grid/checkout formula difference, lexicographic row order, and basket-to-screening aggregation limitation are recorded above. No price-policy correction, numeric row-sort guarantee, or isolated multi-screening guarantee is invented.
  • Push integration limit: iOS contains Firebase messaging setup, but a backend → Firebase/FCM → APNs delivery path was not verified. That path is intentionally absent from the architecture diagram.
  • Validation boundary: this is a source-checked documentation revision, not evidence of a passing iOS build, payment test, backend smoke test, live deployment, or notification-delivery test. Existing SwiftCinemasTests/VenueForMoviesIntegrationTests.swift covers selected location/search contracts; it does not validate all reference entries here.
